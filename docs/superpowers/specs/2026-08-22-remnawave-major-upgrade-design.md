# Мажорное обновление инфраструктуры Remnawave: 2.7.4 → 3.3.2

Дата: 2026-08-22
Статус: согласован, ожидает плана реализации

## Задача

Перевести всю инфраструктуру на мажорную ветку Remnawave 3.x: панель, все ноды,
форк Telegram-бота и форк кабинета. Работы проводятся in-place, в ночное окно,
с допустимым простоем бота до одного часа. Ноды при этом продолжают раздавать
трафик — клиенты подключение не теряют.

|---|---|---|---|

## Ключевые факты, определяющие план

**1. Breaking change панели 3.0.0 — исчезновение UUID пользователей.**
Коммит `drop user uuid, rename user id column`: панель перешла на числовые `id`,
все пользовательские роуты REST API переписаны. Бот v3.64.0 с панелью 3.x
неработоспособен — ломается сразу после апгрейда панели. Значит панель и бот
нельзя разносить по времени, и образ бота v4.1.0 обязан быть собран и лежать в
Docker Hub до того, как мы тронем панель.

**2. Бэкфил идентичности — отдельный ручной шаг.**
Миграция `0104_remnawave_numeric_id` только добавляет колонки `remnawave_id`;
заполнить их она не может, потому что для разрешения панельного аккаунта нужно
обращение к панели по API. До прогона бэкфила у всех доапгрейдных строк
`remnawave_id IS NULL`, а NULL-идентичность трактуется кодом как жёсткая ошибка
данных. Бэкфил запускается только вручную:

    docker compose run --rm bot python -m scripts.backfill_remnawave_ids            # dry run
    docker compose run --rm bot python -m scripts.backfill_remnawave_ids --apply    # запись

Dry-run — режим по умолчанию. Пасс `--apply` отказывается коммитить, если две
строки бота претендуют на один панельный аккаунт. Отчёт пишется JSON-файлом в
`/app/logs` (на msk3 примонтирован как `./logs`, переживает `run --rm`).

Автозапуска на старте бота нет — в `app/` нет ни одного вызова
`backfill_remnawave_ids`, кроме CLI-скрипта.

**3. Ack-переменная не нужна.**
`I_UNDERSTAND_REST_API_BREAKING_CHANGES` присутствовала только в dev-сборках и
была удалена из `docker-entrypoint.sh` до релиза. В теге 3.3.2 энтрипойнт —
обычный `prisma migrate deploy` + `db seed`. Цепочка миграций 2.7.4 → 3.3.2
применяется последовательно, промежуточные версии ставить не требуется.

**4. Единственный breaking change конфига бота нас не касается.**
`TRAFFIC_EXCLUDED_USER_UUIDS` → `TRAFFIC_EXCLUDED_USER_IDS`. В `.env` на msk3
переменная пустая, так что это переименование строки без смены значения.

**5. nl1 изолирован.**
nl1 — единая точка отказа (socks5-прокси бота, inbound webhook relay,
SMTP-туннель кабинета) и одновременно нода. Проверено: `tg-proxy` и `tg-socks` —
standalone-контейнеры без compose-проекта, `remnanode` — отдельный проект в
`/opt/remnanode`. `docker compose up -d` в этой директории их не затрагивает.

## Стратегия

Две фазы. Всё тяжёлое и непредсказуемое выносится из окна; в окне остаются
только `up -d` и проверки.

### Фаза 0 — подготовка (день, без простоя)

1. **Мердж форков.** Бот `v3.64.0 → v4.1.0`, кабинет `v1.61.0 → v1.66.0`.
   Кастомизации форка бота: deploy glue (`docker-compose.yml`, `ci.yml`,
   `Dockerfile`, `.env.example`, логотип), Telegram send-retry, конфиг
   `TELEGRAM_API_URL`/`PROXY_URL`. Кастомизации кабинета: `docker.yml` и
   защитные `stats?.subscriptions?.` в `src/pages/AdminDashboard.tsx` — этот
   файл конфликтует традиционно, берём рефактор upstream и переносим `?.`.
   Push в `origin main` → CI собирает `:latest`.
   **Гейт:** CI зелёный, образы реально в Docker Hub.

2. **Правка тегов в compose.** Панель `backend:2` → `backend:3`, ноды
   `node:latest` → `node:3`, subscription-page `:latest` → `:8`. Файлы правим,
   `up` не запускаем. Пиннинг на мажор закрывает существующую мину: сейчас ноды
   и subscription-page на `:latest`, и любой случайный `pull` уводит их на 3.x
   при панели 2.7.4.

   На `:latest` осознанно остаются два образа. Бот и кабинет — наши собственные
   сборки из CI, там `:latest` и есть механизм доставки. У routing-updater нет
   ни релизов, ни тегов — `:latest` единственный доступный вариант.

3. **Предгрев образов.** `docker compose pull` без `up` на всех 8 нодах, на msk2
   (панель + subscription-page) и на msk3 (бот, кабинет, routing-updater).
   Образы лежат локально, работающие контейнеры не меняются. Это сводит окно
   рассогласования «панель 3.x против нод 2.7.0» к секундам.

4. **Обновление скрипта бэкапа.** `distillium/remnawave-backup-restore`
   3.2.4 → 4.0.0 через встроенный self-update. Прогнать один тестовый бэкап
   **на ещё не обновлённой панели 2.7.4** — убедиться, что новая версия
   работает и заливается в Telegram.

5. **Фиксация точки отката.** Записать digest'ы всех текущих образов (панель,
   8 нод, subscription-page, бот, кабинет, routing-updater).

не тронув БД бота записью.

## Точка невозврата и откат

Prisma-миграции панели необратимы: откат панели — это восстановление БД из
дампа, а не возврат образа.

Отсюда следствие для консистентности. После `--apply` БД бота ссылается на
числовые идентичности, которых в панели 2.x не существует. Откат назад
означает восстановление **обеих** БД, и они обязаны быть снятыми с одной точки
во времени. Поэтому в шаге 3 дампы снимаются строго при **остановленном боте**:
иначе бот успеет создать пользователя в панели между двумя дампами, и после
восстановления базы разъедутся.

Границы:

- **До шага 9** откат дешёвый: вернуть теги образов на зафиксированные digest'ы
  и восстановить БД панели из дампа шага 3. БД бота не тронута записью.
- **После шага 9** откат — восстановление обеих БД из пары дампов шага 3 плюс
  возврат всех образов на прежние digest'ы.

Приложенные суточные бэкапы (00:00 21 августа) — страховка последнего рубежа, а
не рабочий инструмент. Критические дампы снимаются вручную через `pg_dumpall`,
без опоры на скрипт бэкапа: обновлять инструмент и в тот же момент доверять ему
единственную страховку — плохая идея.

## Рассылки

Отправляются через admin API кабинета, фильтр `all` («Все пользователи»).
Перед каждой отправкой — явное подтверждение оператора.

**T−30 минут:**

> 🔧 **Технические работы**
>
> Через 30 минут начнём обновление инфраструктуры. Примерно на час бот и личный
> кабинет будут недоступны.
>
> **VPN продолжит работать** — подключение не отключится. Возможны
> кратковременные разрывы, клиент переподключится сам.
>
> Недоступны будут только покупка и продление подписки. Если срок вашей
> подписки истекает сегодня — продлите её сейчас.
>
> Напишем, когда закончим.

**После смоук-теста:**

> ✅ **Работы завершены**
>
> Бот и личный кабинет снова работают. Спасибо за терпение!
>
> Если что-то ведёт себя странно — напишите в поддержку.

Предупреждение «продлите сейчас» не косметическое: пока бот лежит,
автопродление и оплаты не проходят, и у кого подписка истекает именно в это
окно, тот останется без доступа.

## Риски

**Бэкфил идентичности — риск №1.** Смягчение: идём на v4.1.0, а не на v4.0.0 —
в релиз-ноутах 4.0.0 полтора десятка багфиксов именно бэкфила (привязка чужого
аккаунта, падение на индексе, откат целиком на single-tariff, повторный
прогон). Плюс обязательный dry-run перед `--apply` как отдельный гейт.

**Мердж шести релизов форка.** Выполняется в Фазе 0, при свете дня, а не в
процессе окна.

**routing-updater.** Поддержка панели 3.0.0 добавлена коммитом от 7 августа,
релизов и тегов у репозитория нет — только `:latest`. Если после обновления он
не заработает, это не блокирует запуск: перестанут автоматически обновляться
правила роутинга, сервис для клиентов при этом работает. Разбираемся отдельно,
окно из-за него не продлеваем.

**Свежесть 3.3.x.** Версия вышла 18–20 августа, багфиксы 3.3.1 и 3.3.2 выпущены
в один день. Риск принят осознанно в пользу единого прыжка в актуальное
состояние.
