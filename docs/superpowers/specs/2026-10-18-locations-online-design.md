# Блок «Локации» на панели статистики кабинета — дизайн

Дата: 2026-10-18 (обновлено 2026-10-19). Статус: на утверждении.

## Зачем

Панель Remnawave считает онлайн **по нодам**. Шесть локаций подписки живут на одной ноде MSK-4
(мост в Европу), и все их пользователи видны как «онлайн на MSK-4». Выходы за мостом (DE-1, FI-1,
FI-2, UK-1) видят только служебного пользователя моста — у них всегда «1». Так же на NL-1 живут две
локации («Нидерланды» и «Нидерланды (с рекламой)»). Владелец хочет видеть, **сколько людей сидит
на каждой локации подписки прямо сейчас**, а на AUTO Европа — через какие выходы их на самом деле
уводит балансир.

Своих данных об этом у панели нет: онлайн xray — по пользователю, не по inbound'у; «Обозреватель
сессий» отдаёт только пользователь → IP → lastSeen, без inbound'а (проверено по
`@remnawave/backend-contract`). Единственный источник — access-лог xray на ноде: в каждой строке
есть inbound, outbound, IP клиента и id пользователя.

## Цели

- На странице кабинета `/admin/dashboard` («Панель статистики») под блоком «Ноды» — блок «Локации»
  в том же визуальном стиле: по карточке на каждую рабочую локацию подписки, на карточке название
  как в подписке и число людей сейчас.
- На карточке AUTO Европа — разбивка по реальным выходам (сейчас FI-1 / FI-2).
- Человек, переключившийся между локациями — в том числе **между разными нодами** — считается
  только на последней (решено с владельцем 2026-10-19).
- Новая локация на одной из пяти нод со счётчиком появляется в блоке сама, без правки кода.

## Не цели

- История и графики — только «сейчас».
- Разбивка по людям (кто именно где) — только числа.
- Изменения в самой панели Remnawave, разделение msk4 на несколько нод — отклонено владельцем как
  перебор.
- Счётчик на выходах DE-1/FI-1/FI-2/UK-1 — они не знают реальных пользователей; к тому же de1/fi2 —
  серверы Паши, туда своё не ставим.

## Анти-цели

- Заметная нагрузка на ноды. Владелец: «если сильная нагрузка — чисто ради статистики не стоит».
  Замер: полный разбор 46 тыс. строк лога на msk4 — 0,18 с; постоянное чтение хвоста — меньше.
- Риск для пользователей VPN: счётчик только читает лог, ничего не меняет в xray, профилях, нодах.
- Задвоение при переключении локаций.

## Как считаем (решено с владельцем)

- **Устройство** = пара (id пользователя, IP клиента). Один телефон, переключившийся с nl1 на msk4,
  приходит с того же IP — поэтому сводится в одно устройство и между нодами.
- Окно — **5 минут**. Меньше нельзя: xray пишет в лог только *новые* соединения, телефон может
  минутами сидеть на одном долгом соединении, и с коротким окном такие люди пропадают.
- **Устройство считается только там, где было его последнее подключение в окне** — на какой бы
  из пяти нод это ни было. Переключился с «Нидерландов» на «Германию» — сразу считается только в
  «Германии».
- Число на карточке = число **уникальных пользователей**, у которых хотя бы одно устройство сейчас
  на этой локации. Два устройства одного человека на разных локациях одновременно считаются в обеих
  (он действительно там), поэтому сумма по карточкам может быть чуть больше «Пользователей онлайн»
  — это подписывается на странице одной строкой.
- **AUTO Европа, разбивка:** для устройства, чьё последнее подключение — на `vless-to-eu-auto`,
  берётся outbound его последнего соединения на этом inbound'е, ушедшего в выход-мост (outbound с
  префиксом `SS_OUTBOUND_`; `direct` и `block` не учитываются). Карточка: «N человек», ниже
  «через FI-2 — a, через FI-1 — b» (уникальные пользователи). Имя выхода — из тега:
  `SS_OUTBOUND_FI2` → «FI-2». Устройства AUTO без мостового соединения в окне в разбивку не попадают
  (в общее N — попадают).

## Архитектура

```
5 нод (msk1, msk2, msk4, nl1, SE-1)            msk3: бэкенд кабинета            браузер админа
xray access-лог ─► счётчик (systemd) ──POST/мин──► Redis: последний отчёт ноды ◄── GET /locations
                   устройства за 5 мин              сведение устройств + хосты панели
                   (ключи — HMAC, без id/IP)
```

Сведение между нодами делается на бэкенде, поэтому счётчик отправляет не итоговые числа, а список
устройств за окно. Чтобы не возить по сети id пользователей и IP, ключи псевдонимные.

## Счётчик на ноде

- Один файл на Python 3 только со стандартной библиотекой (на nl1/SE-1 — 3.10, на msk1/msk2/msk4 —
  3.12), в репозитории бота в `scripts/location_counter/` вместе с unit-файлом systemd, примером
  env-файла и README по установке.
- Долгоживущий процесс под systemd (`Restart=always`): читает
  `docker exec remnanode tail -F -n +1 /var/log/xray/current` (или эквивалент) построчно.
  **Почему не cron с разбором всего файла:** лог внутри контейнера режется по размеру (~2–10 МБ,
  окно от часа до двух суток в зависимости от ноды), старые куски удаляются, и сразу после обрезки
  в файле меньше 5 минут. Долгоживущий процесс держит состояние устройств в памяти и не теряет его при
  обрезке. При перезапуске он дочитывает текущий файл с начала — этого достаточно. Если контейнер
  `remnanode` перезапустился и `docker exec` завершился — процесс выходит с ошибкой, systemd поднимает
  его заново.
- Строка лога: `YYYY/MM/DD HH:MM:SS.micro from IP:port accepted proto:dest [INBOUND -> OUTBOUND] email: ID`
  (стрелка бывает `->` и `>>`; встречается `from tcp:IP:port` — учесть). Время — UTC независимо от
  пояса хоста. Строки другого вида пропускаются.
- Состояние: устройство → (время последнего подключения, inbound последнего подключения, последний
  мостовой outbound на этом inbound'е). При смене inbound'а мостовой outbound сбрасывается.
- Раз в 60 секунд — выбросить устройства, у которых последнее подключение старше 5 минут по часам
  хоста (UTC), и отправить POST в кабинет:
  `{"node": "MSK-4", "generated_at": "2026-10-19T07:40:00Z", "window_seconds": 300,
    "devices": [{"u": "<HMAC user>", "d": "<HMAC user|ip>", "t": "2026-10-19T07:39:12Z",
                 "inbound": "vless-to-eu-auto", "exit": "SS_OUTBOUND_FI2"}, ...]}`
  `u` = HMAC-SHA256(токен, id пользователя), `d` = HMAC-SHA256(токен, id + "|" + IP), усечённые до
  16 hex-символов. Токен общий для всех нод — иначе ключи не совпадут. Объём — ~150 устройств ×
  ~120 байт ≈ 20 КБ в минуту с самой загруженной ноды.
- Имя ноды в отчёте — как в панели (`MSK-1`, `MSK-2`, `MSK-4`, `NL-1`, `SE-1`), задаётся в env-файле.
- Ошибка отправки — записать в journal и ждать следующей минуты, без очередей и повторов.
- Адрес кабинета, токен и имя ноды — в `/etc/location-counter.env`, права 600.
- Проверено 2026-10-18/19 на всех пяти: лог в контейнере `remnanode` по пути `/var/log/xray/current`,
  формат одинаковый, `https://cabinet.zanity.net/` отвечает 200 с каждой. На nl1 две локации — разные
  inbound'ы: «Нидерланды» = `vless-inbound-sni-github` (:443), «Нидерланды (с рекламой)» =
  `vless-inbound-with-ads` (:3443). На msk1 и msk2 — по одной локации (`vless-inbound-3443`).
  На msk2 же работает панель; счётчик её не касается. SSH на SE-1 — по IP `root@191.44.114.69`
  (имя `se1.zanity.net` не в known_hosts).

## Бэкенд (этот репозиторий, выкатывается сам при пуше в main)

- `POST /cabinet/admin/stats/locations/report` — приём отчёта. Авторизация — заголовок с общим
  секретом из новой настройки `LOCATION_COUNTER_TOKEN` в `app/config.py` (пусто — эндпоинт отвечает
  404 и фича выключена). Отчёт целиком кладётся в Redis под ключом по имени ноды с TTL 3 минуты.
- `GET /cabinet/admin/stats/locations` (под той же админской авторизацией, что `/admin/stats/nodes`):
  1. Берёт свежие отчёты всех нод из Redis.
  2. **Сведение:** для каждого ключа устройства `d` оставляет запись с наибольшим `t` среди всех нод;
     записи с `t` старше 5 минут от текущего времени отбрасывает.
  3. По оставшимся устройствам считает уникальных `u` на каждую пару (нода, inbound) и, для
     inbound'ов с `exit`, уникальных `u` по выходам.
  4. Накладывает на список локаций из хостов панели (ниже).
  Отдаёт список карточек: название, нода, число людей (или `null` = нет данных), разбивка по выходам
  (только где есть), источник (`counter` / `panel`), время отчёта.
- **Нода без свежего отчёта** (счётчик упал): если на ней одна локация — число = `usersOnline` ноды
  из панели, источник `panel` (без сведения между нодами); если несколько — `null`. На странице такие
  карточки помечаются, чтобы было видно, что счётчик молчит.
- Отдельным эндпоинтом, а не полем в `/admin/stats/dashboard`, чтобы сбой хостов панели или Redis не
  ломал остальной дашборд.
- Путь в клиенте фронта — с префиксом `/cabinet` (traefik срезает `/api`, иначе тихий 404).

### Список локаций

Строится из хостов панели (`GET /api/hosts` через существующий клиент Remnawave): хосты
`isDisabled = false` и `isHidden = false`; разделители (в названии есть «👇») пропускаются.
*(Решение дизайнера: скрытый хост пользователь в подписке не видит — значит, это не локация. На
2026-10-18 скрытых хостов нет; у выходов DE-1/FI-1/FI-2/UK-1 хостов нет вовсе.)*
Хост → нода: готовая `hosts_for_node` в `app/services/reachability/targets.py` (сначала по UUID
inbound'а среди `active_inbound_uuids` ноды, потом по адресу/IP) — переиспользовать. Хост → тег
inbound'а: по `configProfileInboundUuid` через inbounds config-profile — вызова в клиенте пока нет,
добавить. Порядок карточек — как в подписке (`viewPosition`). Если два хоста указывают на одну пару
(нода, inbound) — одна карточка с названием первого. Если одна пара (inbound, профиль) активна на
нескольких нодах, а хост указывает адресом на одну из них — карточка относится к ноде, найденной
`hosts_for_node`.

## Фронт (`~/dev/bedolaga-cabinet`, выкатывается вручную)

- `src/pages/AdminDashboard.tsx`: секция «Локации» сразу под «Нодами», та же сетка карточек,
  тот же приём «показать ещё / скрыть» после трёх. Загружается вместе с остальными данными страницы
  и по кнопке «Обновить».
- Карточка: название локации (с флагом из названия), подпись ноды мелко, крупно число людей
  («—» при `null`), у AUTO — строки разбивки по выходам. Источник `panel` — малозаметная пометка
  «по данным панели».
- Под заголовком блока одна строка пояснения: «Активные за 5 минут, каждое устройство — на последней
  локации. Человек с устройствами на разных локациях считается в каждой».
- Тексты — через i18n, как у блока «Ноды» (`adminDashboard.locations.*`), минимум ru и en.

## Ограничения и известные ловушки

- **Шум Gemini в разбивке AUTO (принято как погрешность — решение дизайнера).** Gemini на msk4 идёт
  через `GEMINI_BALANCER` (DE1/FI1/FI2/UK1), блокированное AUTO — через `SS_EU_BALANCER`
  (DE1/FI1/FI2/NL1/SE1/UK1); в строке лога виден только итоговый outbound, не балансир. Если последнее
  мостовое соединение устройства AUTO было к Gemini, оно попадёт в выход Gemini. Оба балансира
  leastPing по пересекающимся спискам и обычно выбирают одно и то же; отдельно не фильтруем.
- Одно устройство за NAT оператора и другое устройство того же пользователя с тем же IP сольются
  в одно — на число людей это не влияет (считаем уникальных пользователей).
- Часы нод должны быть синхронизированы (NTP); расхождение в секунды на результат не влияет.
- Inbound `vless-to-de2-ss` — это «Великобритания» (историческое имя); названия берём только
  из хостов, по тегам ничего не угадываем.
- Выключенные 🎬-хосты на msk4 не показываем, хотя их inbound'ы ещё живы.
- Новые выходы-мосты в профиле msk4 подхватываются сами: имя выхода из тега.

## Оставлено исполнителю

- Точный формат заголовка авторизации, имена модулей и схем Pydantic.
- Вёрстка карточки в пределах стиля блока «Ноды».
- Тесты: разбор строк лога и логика «последнее подключение устройства» в счётчике — обязательно;
  сведение устройств между нодами и сборка списка карточек на бэкенде — обязательно; фронт — по
  обычной практике репозитория.

## Выкатка

1. Бэкенд → main (автодеплой на msk3), задать `LOCATION_COUNTER_TOKEN` в `.env` на msk3.
2. Счётчик на msk4 первым, проверить, что отчёт приходит; затем nl1, SE-1, msk1, msk2. Изменения на
   серверах — только после явного «да» владельца на выкатку.
3. Фронт кабинета — ручной деплой.

Откат: остановить юниты счётчика (`systemctl disable --now location-counter`) — блок перейдёт на
числа панели там, где на ноде одна локация, и «—» на msk4/nl1. Полное отключение — пустой
`LOCATION_COUNTER_TOKEN`.
